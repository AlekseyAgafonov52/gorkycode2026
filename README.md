# Парсер вакансий

Развёртывание приложения и PostgreSQL: [Docker Compose](DEPLOYMENT.md). Модели, миграции и CRUD: [слой хранения](DATABASE.md).

Основные операции платформы: [HR API и импорт вакансий/откликов](HR_API.md). Swagger: http://localhost:8000/docs.

Передача рекомендаций HR, подтверждение найма руководителем и закрытие вакансии HR: [Telegram-бот департамента](DEPARTMENT_BOT.md).

Интерфейс HR подключён к этому API: вакансии, отклики, JSON-отчёты и сохранение результата звонка в PostgreSQL.
Запуск всей связки: `docker compose up -d --build`, затем http://localhost:5173/.
Настройки и отдельный запуск: [frontend/README.md](frontend/README.md).

Backend адаптирован под контракт MVP: светофор и доля навыков, отчёт с тремя строками итога,
шаблонные вопросы по пропускам, пул вопросов YandexGPT на вакансию и сохранённый выбор для каждого отклика.
Основные схемы — `contract_models.py`, сопоставление — `candidate_analysis.py`, пул — `question_pool.py`,
промпт — `prompts/question_pool.txt`. Данные готовятся командой `python -m hr_api.import_data`;
GET не вызывает модель. Предыдущий CLI ниже остаётся отдельным инструментом.

Модуль ТЗ №3 — генерация уточняющих вопросов через YandexGPT: [инструкция и запуск](QUESTION_GENERATOR.md), код `question_generator.py`.

Проверка одного готового отклика: `.\.venv\Scripts\python.exe check_candidate.py frontend 1`. Основной источник — `job_vacancy.txt` в папке откликов, дополнительный — только раздел «Обязанности» из `job_instruction.docx`. Результат сохраняется в подпапку `questions` в JSON и Markdown.

Для пяти IT-ролей автоматически выбираются разные профили промптов из `prompts/questions/it/`. Общие правила генерации и проверки — `prompts/questions/generation.txt` и `review.txt`. Офлайн-просмотр выбранных текстов: `check_candidate.py --all --prepare-only`, файлы `questions/prompts_1.json`.

Для использования независимо от API:

```python
from vacancy_parser import parse_vacancy, parse_vacancy_file

vacancy = parse_vacancy_file("Вакансия.txt")
data = vacancy.model_dump()
json_text = vacancy.model_dump_json(indent=2)
```

Все поля присутствуют в каждом ответе. Неизвестные скалярные значения — `null`, списки — `[]`. Явное отсутствие требований к опыту — `0`; месяцы переводятся в доли года. Если указано несколько числовых требований к опыту, выбирается максимальное минимальное значение. Гибрид включает формулировку «офис или гибрид».

`required_skills` и `preferred_skills` содержат нормализованные технологии; прочие обязательные требования сохраняются в `additional_requirements`, прочие желательные — в `preferred_skills`. Нераспознанные технологии не теряются: исходные пункты остаются в `original_requirements.required/preferred`. `original_requirements` также хранит исходные требования к образованию и опыту; `source_text` сохраняет весь декодированный документ, включая исходные переносы строк и версии технологий. Это дополнительные поля к формату из задания.

Поддерживаются UTF-8, UTF-8 BOM, UTF-16 BOM и Windows-1251. Заголовки разделов и словарь технологий расширяются в `vacancy_parser.py`. Название берётся из явного поля либо первой строки; организация — из явного поля либо полного наименования в кавычках; город — из явного поля либо строки после дохода в экспорте HeadHunter.

Парсер на правилах не гарантирует полноту извлечения из произвольного естественного языка. Незнакомые формулировки остаются в исходном тексте; факты не выводятся из названия должности или контекста компании. Содержимое документа обрабатывается как данные. Сопоставление навыков для MVP выполняется отдельно в `candidate_analysis.py`.

## Парсер откликов

`response_parser.py` — отдельный локальный парсер под шаблон предоставленных откликов. Работает без GPT, API-ключей и отправки резюме во внешние сервисы. Используется один алгоритм для Frontend, Junior Python, UX/UI, Python и QA; условия по номерам кандидатов отсутствуют.

### Что извлекается

Pydantic v2 схема `CandidateResponse` содержит одинаковые поля для всех файлов:

| Поле | Содержимое |
| --- | --- |
| `candidate_id`, `resume_title` | Номер кандидата из текста и название резюме |
| `cover_letter`, `about_me` | Письмо и раздел «Обо мне» |
| `experience_total_months`, `similar_experience_months` | Общий стаж и стаж в похожих должностях, указанные в экспорте, в месяцах |
| `work_experience` | Места работы: даты `YYYY-MM`, признак текущей работы, указанная длительность, организация, должность, строки о работодателе, описание и исходный блок |
| `skills` | Все явно перечисленные навыки, включая нетехнические, с нормализованным названием, исходным названием и уровнем |
| `languages` | Языки, `native` / CEFR A1–C2, описание уровня и исходная строка |
| `education_level`, `education` | Уровень образования, записи с учреждением, дополнительными строками, указанным годом, уровнем и исходным блоком |
| `additional` | Время в пути, командировки, гражданство, разрешение на работу, вождение, самозанятость, медкнижка — исходные строковые значения |
| `original_sections`, `source_text` | Исходные разделы и весь декодированный текст |
| `warnings` | Отсутствующие заголовки и поля, неоднозначные должности, нераспознанные записи |

Уровни навыков: `advanced`, `intermediate`, `basic`, `null`. Например, `VueJS` → `Vue.js`, `Vue3` → `Vue.js 3`, `Docker-compose` → `Docker Compose`, `Photoshop` → `Adobe Photoshop`, `Corel Draw` → `CorelDRAW`, `jmeter` → `Apache JMeter`, `k8s` → `Kubernetes`. Версии Vue/Python сохраняются; исходные названия доступны в `skills[].original`. Неизвестные навыки сохраняются без переименования. Навыки берутся из раздела «Навыки»: упоминания технологий в письме или описаниях работ доступны в соответствующих текстовых полях и не превращаются автоматически в подтверждённые навыки.

Отсутствующие данные — `null` или `[]`. «Не указано в доступной версии резюме» не превращается в нулевой стаж. Явное «Без опыта работы» — `0`. Общий стаж берётся из отдельной строки; пересекающиеся периоды работ не суммируются и текущий стаж не пересчитывается на сегодняшнюю дату. Год образования передаётся как указан в тексте, включая будущий год, без утверждения о завершении обучения.

Повторные заголовки внутри описания работы и «Обо мне» остаются частью исходного рассказа. Основной список навыков определяется по положению перед разделом языков с маркером «Родной» / «Другие языки». Раздел «Образование» определяется по следующей строке «Уровень», а «Дополнительно» — по именованному полю. Поддерживаются как «Организация N», так и настоящие названия работодателей. Если учреждение и специальность объединены в одну строку, эта строка целиком остаётся в `institution`: разделение не угадывается. Город работодателя сохраняется в `employer_details` и не считается местом проживания кандидата. Название резюме берётся из самого документа, даже если оно не соответствует вакансии, на которую подан отклик.

### Все предоставленные отклики

```powershell
python parse_responses.py "D:\Кадры\Frontend developer" "D:\Кадры\Junior Python-разработчик" "D:\Кадры\Junior UX_UI Дизайнер" "D:\Кадры\Python-разработчик" "D:\Кадры\QA Engineer Manual" --output parsed_responses
```

Обрабатываются файлы `отклик N.txt` непосредственно в выбранных папках. Вакансии не включаются. Нумерация кандидатов в каждой папке начинается заново, поэтому сохраняется иерархия:

```text
parsed_responses/
  Frontend developer/отклик 1.json … отклик 99.json
  Junior Python-разработчик/отклик 1.json … отклик 430.json
  Junior UX_UI Дизайнер/отклик 1.json … отклик 212.json
  Python-разработчик/отклик 1.json … отклик 309.json
  QA Engineer Manual/отклик 1.json … отклик 384.json
  _report.json
  _schema.json
  _verification.json
```

`_report.json` содержит результат для каждого файла, ошибки и предупреждения; `_schema.json` — JSON Schema. Повторный запуск перезаписывает соответствующие результаты и отчёт. Ошибка отдельного отклика не останавливает обработку остальных; код завершения `1` означает наличие ошибок. Предупреждения дают код `0`.

### API

Тот же сервер `main:app`, новый маршрут: `POST /api/v1/parse/response`. Multipart-поле `file`, TXT до 2 МиБ, те же кодировки и коды ошибок, что у API вакансий.

```powershell
curl.exe -F "file=@D:\Кадры\Frontend developer\отклик 1.txt" http://127.0.0.1:8000/api/v1/parse/response
```

### Проверка

```powershell
python -m unittest -v
python verify_responses.py --root "D:\Кадры" --output parsed_responses
```

Модульные тесты используют синтетические тексты и не требуют папки `D:\Кадры`. `verify_responses.py` отдельно проверяет все 1434 предоставленных TXT из пяти папок и сохранённые JSON: структуру Pydantic, номера кандидатов, сохранность навыков, записей работ, образования и исходного текста, а также совпадение ответов API с пакетными результатами. Сохраняет `_verification.json`. Список папок и ожидаемое число файлов для этой проверки находятся в `CORPUS`; сам пакетный парсер принимает произвольные папки.

Результат обработки предоставленной выборки: 1434/1434 файлов, 3571 место работы, 29761 запись навыков, 1840 записей образования. В 20 откликах есть предупреждения об отсутствующем названии резюме или невыделенной должности. Соответствующие поля оставлены `null`, исходный текст сохранён. Дополнительные работодатели, перечисленные внутри свободного описания работы, остаются в описании, без создания дублирующих мест работы. Полные результаты проверки каждого файла и API находятся в `_report.json` и `_verification.json`.

Это парсер конкретного формата экспорта. Для иного порядка разделов, другого оформления дат или свободного резюме потребуется расширение правил. Оценка кандидатов и сравнение с вакансией не выполняются.
