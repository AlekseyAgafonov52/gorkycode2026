# HR API

Базовый префикс `/api/v1`. Swagger доступен на http://localhost:8000/docs. Реализованы 11 операций из ТЗ и два существующих парсера. Идентификаторы объектов — UUID; существующий номер кандидата сохраняется внутри исходного JSON.

| Метод и путь | Назначение |
| --- | --- |
| `GET /vacancies` | Вакансии и число откликов |
| `GET /vacancies/{id}` | Исходные характеристики в `source_json`, критерии и их версия |
| `PATCH /vacancies/{id}/criteria` | Изменить важность критериев |
| `GET /vacancies/{id}/responses` | Отклики, сортировка по оценке, фильтры |
| `GET /responses/{id}` | Карточка, исходный JSON, структурированные сведения и состояние отчёта |
| `POST /vacancies/{id}/match` | Фоновая заглушка сопоставления, HTTP 202 |
| `GET /tasks/{id}` | Состояние фоновой задачи |
| `GET /responses/{id}/report` | Сохранённый отчёт и вопросы |
| `POST /responses/{id}/questions/generate` | Поставить генерацию вопросов в очередь, HTTP 202 |
| `PATCH /responses/{id}/status` | Статус обработки |
| `PATCH /responses/{id}/archive` | Архивировать или восстановить |

## Основные запросы

Изменение критериев:

```json
{"criteria": [{"id": "<criterion-uuid>", "importance": "required"}]}
```

Допустимы `required`, `preferred`, `irrelevant`. Поле `name` можно передать для проверки, но переименование этим эндпоинтом не выполняется. Пакет изменяет `criteria_version` один раз, только если значения изменились, и ставит сопоставление в очередь. В ответе возвращается `task_id`; при отсутствии изменений он равен `null`.

Изменение статуса и архива:

```json
{"workflow_status": "reviewed"}
```

```json
{"is_archived": true}
```

Статусы обработки: `new`, `reviewed`, `contacted`. Они независимы от цвета. Архив не удаляет отклик или отчёт. Публикация реального красного результата через сервисный метод архивирует отклик; HR может восстановить его отдельно. Заглушка цвет не присваивает.

Список откликов принимает `match_status`, `workflow_status`, `is_archived`, `limit` и `offset`. По умолчанию показаны неархивные отклики, до 1000 записей. Сортировка — по убыванию актуальной оценки; неизвестные и устаревшие оценки находятся в конце. Пока сопоставление не реализовано, `match_score`, `match_status`, `missing_data_count` равны `null`.

## Задачи и отчёты

Статусы задач: `pending`, `processing`, `completed`, `failed`. Сопоставление помечено `is_stub=true`: успешное завершение такой задачи не означает расчёт оценки. FAISS/трансформер не вызываются, фиктивных результатов в `match_results` не создаётся.

Задачи сохраняются в PostgreSQL и обрабатываются отдельным `worker`. Advisory lock оставляет одного активного обработчика на базу. При перезапуске worker незавершённые задачи возвращаются в очередь; внешний запрос к модели после прерывания может быть повторён. Повторная постановка уже активной задачи возвращает тот же `task_id`.

Генерация использует существующий клиент YandexGPT, настройки из `.env` и промпты `prompts/hr_api/`. В модель передаются только `skills` кандидата, обязательные критерии, актуальные результаты сопоставления и недостающие сведения. Полный текст резюме не отправляется. Вопросы проходят проверку схемы, принадлежности обязательному критерию, повторов и отдельную проверку моделью. Технические вопросы могут содержать `expected_answer` и `follow_up_hint`.

GET-запросы не вызывают модель. Вопросы сохраняются в таблице `questions`. Повторный POST использует текущий сохранённый результат; тело `{"force": true}` запрашивает повторную генерацию. Если обязательных критериев нет, задача завершается с пустыми вопросами без YandexGPT.

При изменении критериев старые активные задачи помечаются заменёнными. Их результаты не публикуются. После фоновой заглушки заново генерируются вопросы только для откликов с ранее запрошенным отчётом. Массовая генерация по ещё не открытым откликам не запускается.

`report.state`: `not_ready`, `pending`, `processing`, `partial`, `ready`, `stale`, `failed`. `partial` означает, например, наличие вопросов при ещё не выполненном сопоставлении. Устаревшие вопросы и оценки не выдаются как актуальные; старые записи сохраняются в БД. Неизвестное ФИО равно `null`.

Ошибки: 404 — объект не найден; 422 — неверное тело, UUID, фильтр или чужой критерий; 409 — конфликт версии; 503 — PostgreSQL не настроен или недоступен. Ошибки фоновой генерации отражаются в задаче без публикации исходных данных и ключей.

## Импорт и запуск

```powershell
docker compose up -d --build
docker compose exec api python -m docker.entrypoint python -m hr_api.import_data
```

Импорт использует пять папок `parsed_responses` и имеющиеся JSON вакансий из `vacansies`; для остальных вакансий читается сохранённый TXT. UUID детерминированы по профилю и номеру отклика. Повторный импорт не создаёт дубликатов и не перезаписывает изменения HR. Исходные JSON сохраняются целиком. Критерии формируются из явных обязательных/желательных навыков и дополнительных требований, без LLM.

Запуск без Docker: сначала примените миграции, затем в отдельных процессах выполните `python -m uvicorn main:app --reload` и `python -m hr_api.worker`. Для интеграционных тестов задайте отдельный `TEST_DATABASE_URL`; реальные вызовы YandexGPT в тестах заменены транспортом или провайдером.
