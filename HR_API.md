# HR API по контракту MVP

Backend: http://localhost:8000, Swagger: http://localhost:8000/docs, префикс `/api/v1`.
CORS разрешает `http://localhost:5173`. Идентификаторы — строки UUID.

## Основные эндпоинты

| Метод и путь | Ответ |
| --- | --- |
| `GET /vacancies` | `[{id, title, responses_count}]` |
| `GET /vacancies/{id}/responses` | `[{id, candidate_name, match_status, match_share, short_summary, workflow_status}]` |
| `GET /responses/{id}/report` | Сохранённый отчёт по схеме `ContractReport` |
| `PATCH /responses/{id}/status` | `{id, workflow_status}` |
| `PATCH /responses/{id}/viewed` | `{id, is_viewed}` — ручная отметка просмотра HR |
| `PATCH /responses/{id}/source-text` | Отредактировать текст и получить обновлённый `ContractReport` |

Статус обработки: `new`, `forwarded`, `not_forwarded`. Например:

```json
{"workflow_status": "forwarded"}
```

Статус хранится независимо от цвета, переживает перезапуск и повторный импорт.
Отметка просмотра хранится отдельно в `is_viewed: boolean` и возвращается в списке откликов,
карточке и отчёте. Начальное значение — `false`. Открытие отчёта автоматически его не меняет.
Для ручной отметки отправьте `PATCH /responses/{id}/viewed` с `{"is_viewed": true}` или `false`.
API требует JSON boolean: строки `"true"`/`"false"`, числа и `null` отклоняются с 422.
GET списка поддерживает фильтр `?is_viewed=true` / `false`. Просмотр не меняет цвет,
результат звонка, архив, вопросы и кэш анализа.
Ошибки имеют вид `{"error":{"code":"not_found","message":"..."}}`:
404 `not_found`, 422 `validation_error`, 500 `internal_error`.
Неизвестная строка ID (в том числе `nope`) возвращает 404.
Старые multipart-парсеры дополнительно используют 413 и 415 с тем же конвертом ошибки.

## Отчёт и светофор

Схемы находятся в `contract_models.py`. Отчёт содержит все поля контракта:
`id`, `vacancy_id`, `candidate_name`, `contacts`, `match_status`, `match_label`,
`match_share`, `summary`, `skills`, `missing_data`, `ai_text_level`, `short_summary`,
`workflow_status`, `source_text`, а также добавленную по запросу HR отметку `is_viewed`.

`summary` — ровно три строки. `source_text` — исходный текст без изменений.
`ai_text_level` и `short_summary` пока `null`; `follow_up_hint` и `repeat_of` тоже `null`.
У каждого навыка есть уровень из резюме, цвет, объяснение и вопросы.

Правила в `candidate_analysis.py`:

- Итоговый цвет `green` при доле совпадения >= `GREEN_THRESHOLD` (единственная константа, 0.7), иначе `yellow`.
- Отсутствие ФИО и контактов не влияет на оценку. Эти пропуски остаются в `missing_data` как уточнения.
- Явный навык без уровня, со средним или продвинутым уровнем — `green`; базовый уровень или косвенное упоминание — `yellow`; отсутствие — `red`.
- Доля = число навыков с цветом не red / число навыков вакансии. При пустом списке — 0.
- Явные теги «Ключевые навыки» имеют приоритет; при их отсутствии используются требования. VueJS и Vue 3 приводятся к Vue.js.

Отклики сортируются green → yellow, внутри цвета — по убыванию доли. Автоматического отклонения нет.
Навыки в отчёте сортируются red → yellow → green: red здесь означает отсутствие конкретного навыка.
По умолчанию видны все отклики. Необязательные фильтры: `match_status`, `workflow_status`,
`is_archived`, `is_viewed`, `limit` (до 1000), `offset`.

## Подготовка и вопросы

Независимые функции:

```python
from candidate_analysis import parse_resume, extract_vacancy_skills, match
from question_pool import build_question_pool, pick_questions
```

`resume_from_json` адаптирует готовый JSON без повторного парсинга резюме.
`ReportPreparer` вызывает функции при загрузке или в фоновой задаче и сохраняет результат в PostgreSQL.
GET читает готовые данные без сопоставления и вызовов LLM.

На вакансию выполняется один запрос YandexGPT, по два вопроса с ответом на каждый навык.
В модель передаются только текст вакансии и список навыков; данные кандидатов не передаются.
Промпт: `prompts/question_pool.txt`. Модель и ключ: `YANDEX_MODEL_URI` и настройки Yandex в `.env`.
Готовый пул сохраняется в `vacancies.question_pool`; повторная загрузка использует его.
Изменение текста вакансии, набора навыков или промпта требует нового пула при следующей обработке.
При сетевой ошибке/невалидном пуле обработка завершается ошибкой; фиктивных ответов нет.
После прерывания до сохранения пула повторная обработка может повторить внешний вызов.

Для найденного навыка локально выбирается один случайный вопрос из пула; выбор сохраняется в отчёте.
Для отсутствующего навыка создаётся один шаблонный вопрос `kind: missing`, без LLM.
`missing_data` содержит по одному вопросу для недостающих ФИО, телефона, email, Telegram и стажа.
Все вопросы сохраняются в `questions`, вложенная форма отчёта — в `reports.contract_json`.
Неизменившийся отклик повторно не обрабатывается; вопросы и их ID остаются прежними.

## Запуск и импорт

```powershell
docker compose up -d --build
docker compose exec -T api python -m docker.entrypoint python -m hr_api.import_data
```

Импорт загружает пять текущих папок `parsed_responses`. Готовый JSON имеет приоритет перед TXT того же отклика.
Исходные JSON остаются целыми. UUID определяются постоянным ключом папки и номером отклика;
повторный запуск не создаёт дубликатов и не перезаписывает изменения HR.
Команда по умолчанию также готовит отчёты. `--data-only` пропускает подготовку и внешние вызовы.

Для другой папки с `Вакансия.txt` / `job_vacancy.txt` и `отклик N.txt` / `отклик N.json`:

```powershell
python -m hr_api.import_data --folder "D:\Данные\Новая вакансия" --key stable-source-key
```

Ключ должен оставаться одинаковым при повторном импорте и отличаться у разных источников.
Изменение ранее импортированного исходного файла не перезаписывает запись в БД автоматически.

## Дополнительные операции

Сохранены существующие эндпоинты карточки вакансии, критериев, карточки отклика, архива,
фоновой обработки, состояния задач и два TXT-парсера. С редактированием резюме доступно 15 операций.
`POST /vacancies/{id}/match` теперь готовит отчёты по алгоритму контракта, `is_stub=false`.
`POST /responses/{id}/questions/generate` готовит один отчёт из пула вакансии.
`force: true` создаёт новую задачу, но не сбрасывает актуальный пул и стабильный отчёт.
Для изменения вопросов измените промпт и запустите обработку вакансии.
FAISS и трансформер не используются.

Worker один на базу благодаря advisory lock. Задачи сохраняются в PostgreSQL и переживают перезапуск.
Статусы: pending, processing, completed, failed. Подробности входных данных и ключи в ошибках не публикуются.
Изменение критериев повышает `criteria_version`, отменяет старые задачи и ставит подготовку вакансии в очередь.
Устаревший/неподготовленный отчёт временно возвращает 500 с понятным сообщением до подготовки.
Без Docker запускайте миграции, API и `python -m hr_api.worker` отдельными процессами.

## Проверка

`test_hr_api.py` проверяет T1–T13 контракта, импорт TXT/JSON, CORS, ошибки, задачи,
повторное чтение, устаревание, отказ провайдера и гонку изменения критериев.
Тестовые имена и контакты вымышленные, домен `example.com`. Оригиналы не изменяются.
Без `TEST_DATABASE_URL` интеграционные проверки пропускаются. Для полного прогона задайте URL
отдельной тестовой PostgreSQL-базы (не рабочей), затем `python -m unittest discover`.
Тесты используют случайные схемы и заменяют YandexGPT тестовым генератором.

Старый CLI `check_candidate.py` и `question_generator.py` оставлен самостоятельным инструментом
из предыдущего ТЗ. Его персональные вопросы и промпты не используются новым MVP API.

## Демо на откликах организаторов №1–3

В исходных откликах нет ФИО; это не мешает оценке по навыкам.
Для показа заполненных ФИО и контактов можно создать отдельные демонстрационные копии:

```powershell
python -m hr_api.demo_data --output .local/contract-demo
python -m hr_api.import_data --folder .local/contract-demo --key demo-frontend
```

ФИО и email `example.com` добавляются только в копии №1 и №3, №2 остаётся исходным.
Папка содержит `DEMO.txt`, а изменённые тексты помечены «ДЕМОНСТРАЦИОННЫЕ ДАННЫЕ».
Существующие исходники и рабочие записи не меняются. Требуется пустая папка назначения.
Если демо-папка уже создана, пропустите команду создания и используйте команду импорта.

Правило оценки обновлено по уточнению пользователя: прежний пункт контракта о красном цвете из-за ФИО/контактов отменён.
При переходе с версии подготовки 1 на 2 меняются только итоговый цвет и подпись; выбранные вопросы и их ID сохраняются.

## Редактирование исходного текста

`PATCH /api/v1/responses/{response_id}/source-text` принимает:

```json
{"source_text": "Новый текст резюме", "expected_source_text": "Текст, который был открыт в редакторе"}
```

`source_text` — непустая строка до 2 097 152 символов, без NUL. Пробелы и переносы строк сохраняются как переданы.
`expected_source_text` необязателен для внешних клиентов, но frontend всегда передаёт его для защиты от потери правок.
Если текст уже изменился, ответ — 409 `conflict`, сохранение не выполняется.

Локальный парсер заново извлекает данные; поля резюме, контакты, навыки, оценка и вопросы обновляются атомарно.
Используется актуальный сохранённый пул вакансии, вызовов YandexGPT нет. Если пул не подготовлен, ответ — 409.
При ошибке обработки вся транзакция откатывается. Повторное сохранение неизменившегося текста не пересчитывает отчёт.
UUID отклика и существующий `candidate_id`, результат звонка, архив и отметка просмотра сохраняются.
Пользовательские поля исходного JSON сохраняются, производные поля парсера заменяются новыми значениями.
Правки сохраняются в БД; исходные файлы на диске не перезаписываются. Повторный импорт не отменяет правки HR.
Ответ 200 — полный обновлённый отчёт. Неизвестный отклик — 404, некорректный запрос — 422.
# PDF-отчёты на странице отклика

Страница отклика показывает сохранённый PDF на вкладке «Отчёт». `GET /api/v1/responses/{response_id}/report/pdf/preview` возвращает размеры страниц. Тот же запрос с `?page=1` возвращает PNG выбранной страницы; нумерация начинается с единицы.

`GET /api/v1/responses/{response_id}/report/pdf` возвращает PDF (`inline`), `?download=true` — скачивание. Поддерживаются Range-запросы. Если документа нет, возвращается стандартная ошибка 404. В JSON-отчёте поле `pdf_report` содержит имя документа и `is_stale`, либо `null`. При изменении исходного JSON отклика ранее созданный PDF сохраняется, а на странице появляется отметка о предыдущей версии.

Готовые PDF из `otchet_offline/reports_designer`, `otchet_offline/reports_frontend` и `otchet_offline/reports_python` сопоставляются с импортированными откликами по ключу вакансии и номеру кандидата в имени файла. Для дополнительных выгрузок используется индекс `otchet_offline/reports/platform-index.json` с ключом импорта, номерами кандидатов, именами PDF и хешами исходных JSON. Чтобы обновить этот индекс после офлайн-генерации:

```powershell
.\.venv\Scripts\python.exe -m hr_api.index_pdf_reports --key designer
```

При необходимости укажите `--reports` и `--applications`. Ключ `--key` должен совпадать с ключом `hr_api.import_data`. В Docker каталог отчётов подключён к API в режиме чтения. Оригиналы PDF не перемещаются и не изменяются; повторная генерация и вызовы моделей для просмотра не требуются.
